Adaptive Skill Granularity for Coding Agents:
Runtime Routing and Macro-to-Micro Recovery
Dingxuan Zhang1⋆, Yanhui Jiang2⋆, Jun Wang3, and Hefeng Zhou1
1 Shanghai Jiao Tong University, China
2 Kuaishou Technology Co., Ltd., China
3 University of Warwick, UK
h.rezin.zhou@gmail.com
Abstract. Reusable skills allow large language model agents to pack-
age task-specific procedures, tool affordances, and execution guidance
into modular units. Prior work has largely studied how agents retrieve,
compose, or synthesize skills before execution. In coding agents, how-
ever, execution poses an additional runtime control problem: the same
task may be solved through primitive tool calls, macro skills, or hybrid
execution that starts with a macro and falls back to micro-level recovery.
We introduce Adaptive Skill Granularity, a framework that treats skill
granularity as an action-abstraction policy conditioned on task struc-
ture, execution state, and macro-skill failures. The system combines a
feature-based granularity controller and a finite-state recovery executor.
We evaluate the framework with a deterministic coding-agent protocol
using verifier-defined success, total cost, and process metrics such as
macro adoption, failure recovery, route match, and transition correct-
ness. Results show that fixed macro execution is efficient when applicable
but brittle under mismatch, while runtime routing and explicit macro-to-
micro recovery improve robustness and recover controlled macro failures
that fixed-granularity execution leaves unresolved. Our findings suggest
that skill libraries for coding agents should be treated not only as re-
trievable resources, but also as controllable, verifiable, and recoverable
execution abstractions.
Keywords: LLM agents, agent skill, adaptive skill granularity

Introduction
Large language model (LLM) agents increasingly solve software-engineering tasks
by inspecting files, invoking tools, editing code, and validating changes. To avoid
solving each task from scratch, recent systems package reusable procedures
as skills: named artifacts that specify when to act, which tools to use, what
state to inspect, and how to verify completion. Existing skill ecosystems include
Markdown skills, structured runtime skills, skill routers, dependency-aware skill
graphs, and mined trajectory fragments [8, 25–27].

Most prior work treats skill use as a selection or retrieval problem: given a
task and a skill library, expose the most relevant skill text or bundle before plan-
ning [6, 13, 26]. This is necessary but insufficient for tool-using agents. During
execution, the agent must also decide the granularity of its next actions. A sim-
ple bug fix may be safer with micro tools such as search, editing, syntax checks,
and tests, while a module move may benefit from a macro skill that combines file
movement, import rewriting, and validation. When such a macro fails or only
partially applies, the agent needs controlled macro-to-micro recovery rather than
another retrieval step.
This motivates treating skill granularity as a runtime control variable. Recent
evidence shows that injected skills often provide uneven gains, increase cost,
or even degrade software-engineering performance when their abstraction level
does not match the task context [7]. Hierarchical agent methods also adapt
abstraction levels, but usually at the planning level through learned policies or
repeated refinement [10, 19]. In contrast, we control the admissible action set at
runtime: the agent may execute with micro tools, macro skills, or a hybrid mode
that downgrades to micro tools after an observable macro failure. This keeps the
controller inspectable and makes recovery an explicit execution transition rather
than an informal retry or re-planning heuristic.
This paper studies adaptive skill granularity as a runtime control problem.
An LLM agent with a skill library must decide not only which skill description to
retrieve, but also the abstraction level of its next actions. Our central hypothesis
is that no fixed granularity is universally optimal; the best choice depends on
task structure, skill quality, execution state, and verifier feedback. We instanti-
ate this problem in coding agents because repositories provide persistent state,
tools expose concrete side effects, and tests offer deterministic validation. This
makes coding a high-observability testbed while keeping the method defined
over general agent trajectories, action abstractions, and recovery transitions.
We further ground macro-skill admission in a real-world skill-library template,
requiring each candidate macro to document its scope, interface, side effects,
failure behavior, verification procedure, and fallback path before it can enter the
executable library. We make three contributions.
1. We formulate runtime skill granularity control as distinct from ordinary skill
retrieval. The decision is not only which skill to expose, but whether to
execute in micro, macro, or hybrid recovery mode.
2. We present an agent-control architecture, instantiated in coding agents, that
combines a feature-based granularity controller with a finite-state recovery
executor to manage runtime execution abstraction.
3. We define a verifier-driven GranBench-Code evaluation protocol that treats
validated success and total cost as primary metrics, and reports macro adop-
tion, failure recovery, route match, transition correctness, and confidence in-
tervals. We apply it in a pilot study of fixed-granularity, routed, and recovery-
enabled agents, while specifying the unconstrained and LLM-router baselines
required for the full study.

Related Work
Agent skills and routing. Recent work defines agent skills as reusable procedural
artifacts spanning representation, acquisition, retrieval, execution, and evolution
[22, 27]. Runtime-oriented systems such as Formal Skill further package skills
with metadata, schemas, executors, and hooks [25], while SkillCraft evaluates
whether agents can form and reuse higher-level tool compositions [2]. In paral-
lel, SkillRouter, Graph-of-Skills, Skill Is Not Document, and SkillWeaver study
how to retrieve, bundle, or compose relevant skills for a task [6, 13, 20, 26]. In
short, prior works primarily optimize which skills to expose. In contrast, our
work controls how coarsely an agent executes at runtime—dynamically shifting
between primitive tools, macro skills, and recoverable hybrid paths based on live
execution states.
Action abstraction, monitoring, and repair. Our formulation is connected to clas-
sical temporal abstraction, including options, MAXQ, and hierarchical task net-
works [4, 5, 18]. Macro skills can be viewed as temporally extended actions, but
we do not learn an end-to-end hierarchical policy; instead, we use an inspectable
controller to constrain the admissible action set at each run. The downgrade
mechanism also relates to execution monitoring and recovery in planning and
robotics [16], and to automated program repair after failed edits [11]. Compared
with hierarchical LLM-agent methods such as HiMAC and self-adaptive hierar-
chical planning [10, 19], which adapt or refine plans, we treat granularity as a
verifier-grounded runtime control decision over the next available actions.
Skill evolution and coding-agent evaluation. Trajectory-mining systems extract
reusable skills from agent traces [1, 8, 12, 21, 24], but mined fragments may be
brittle. Our macro-evolution loop therefore requires replay, deterministic valida-
tion, documented side effects, and fallback behavior before a macro is admitted.
For evaluation, our protocol follows the executable software-engineering tradition
of SWE-bench [9] and recent calls to assess coding agents by both final correct-
ness and process behavior [14, 15, 23]. Furthermore, recent findings emphasize
that performance gains from function-calling skill injection must be carefully
attributed to distinguish genuine procedural transfer from mere interface com-
pliance [3]. Closest in motivation, SWE-Skills-Bench reports that skill injection
can yield uneven gains and higher cost depending on abstraction level and con-
text fit [7]. Adaptive Skill Granularity targets this failure mode by controlling
when skills should be used, avoided, or downgraded during execution.

4.1
Design Invariants
The framework is constrained by three invariants that make the evaluation au-
ditable.
1. Pre-execution routing only uses pre-execution evidence. The con-
troller in Eq. (3) may inspect task metadata and the initial fixture, but not
verifier outcomes from the current run. This information separation is con-
ceptually analogous to prior-aware evaluation in RAG-based fact-checking [17],
which distinguishes pre-evidence model states from post-retrieval evidence.”
2. Recovery is event-driven. The system may transition from macro to mi-
cro mode only after an observable macro failure, validation failure, fault-
injection event, or explicit recovery-router decision, matching Eq. (5).
3. Success is verifier-defined. A run is successful only when the deterministic
validator passes on the final workspace, regardless of whether the model
declares completion.
4.2
Algorithmic Contract
For each task, the controller first extracts complexity features and produces a
decision tuple
d = (selected_mode, selected_strategy, enable_macro_recovery, reason). (8)


The executor initializes the tool set from d. In macro mode, if a failure occurs
and recovery is enabled, the FSM switches to micro tools and continues from
the current workspace; otherwise, the failure is terminal. Every transition is ap-
pended to the trajectory log before the next action. Eq. (8) records this runtime
execution of Eq. (3), explicitly separating learned routing, recovery decisions,
and validation evidence for analysis.
4.3
Complexity Features
The current implementation uses low-dimensional structural features extracted
before execution:
ϕ(τ) = [npath, npy, nnonpy, nentity, nAST, dAST, nimport, ndep, btext, brefactor].
(9)
These dimensions capture number of source paths, Python and non-Python file
counts, entity-like strings in the prompt, AST node count, maximum AST depth,
import count, cross-file dependency count, text-task flag, and refactor-task flag.
These features intentionally avoid execution-derived information so that the
router does not leak validation outcomes into the decision.
4.4
Granularity Controller
The controller supports heuristic and learned routing. The heuristic is a hand-
written rule set used as a reference baseline. The learned router, trained on prior
execution logs, predicts whether a task starts in micro or macro mode, while an
optional recovery router decides if a macro-compatible task should enable hybrid
fallback. Together, these routers determine g0 and r0 in Eq. (3), while q0 logs
confidence or explanations for auditing.
To ensure interpretability and prevent memorization, the learned router is a
shallow Decision Tree Classifier with a maximum depth of 4. It is trained offline
on empirical success and token cost data, then serialized into JSON. At runtime,
the controller deterministically traverses this lightweight JSON tree using run-
time features, eliminating online retraining and opaque neural checkpoints while
guaranteeing full auditability.
4.5
Macro-Skill Interface
We treat a macro skill as an option-like, temporally extended tool call with an
explicit contract:
m = (name, args, pre, effect, Vm, Fm, fallback),
(10)
where pre describes when the macro is applicable, effect describes allowed workspace
side effects, Vm is an internal verification routine, Fm is the set of observable
failure classes, and fallback records the intended micro-level continuation. This
contract is what lets a macro participate in the recovery transition of Eq. (5): a


failed macro must expose enough state for the executor to decide whether the
current workspace can be repaired with primitive tools.
The current prototype uses three hand-written macros. inspect_python_module
summarizes a module’s symbols, syntax health, and optional pattern matches;
replace_and_verify applies a targeted text replacement and then runs syntax
checks and an optional task-specific test; and move_module_and_update_imports
moves a Python module, rewrites import sites, and validates the resulting workspace.
These macros are deliberately small: they are large enough to expose granular-
ity trade-offs, but constrained enough that their preconditions, side effects, and
verifier behavior can be audited.
4.6
FSM Recovery Executor
The recovery executor treats macro failure as a state transition rather than a
terminal event. Macro calls can fail because the expected text is absent, syntax
checks fail, tests fail, or a fault-injection rule simulates a brittle skill. When recov-
ery is enabled, the executor downgrades to primitive tools and asks the model to
continue from the current workspace. Each run records transition count, macro
failure count, recovery trigger, first failure point, and final validated success.
This executor is the concrete implementation of Eq. (5).

4.7
Macro Evolution Loop
While this paper focuses on the runtime routing and recovery of existing skills, a
practical coding agent must eventually acquire new macro skills. We conceptu-
alize a macro evolution loop as a natural extension of the Adaptive Skill Gran-
ularity framework, leaving its end-to-end empirical evaluation to future work.
To ensure that newly mined skills remain compatible with our FSM recovery
executor, simple trajectory mining is insufficient. We propose that any gen-
erated macro candidate must pass a strict, verifier-grounded admission gate.
Specifically, a candidate must: successfully replay on historical tasks, explicitly
document allowable workspace side effects, and define a precise micro-level fall-
back path or explicitly declare an unrecoverable failure class. By enforcing this
conceptual admission gate, future automated skill discovery systems can prevent
brittle prompt fragments from entering the library, preserving the controllable
and verifiable execution invariants required by our framework.
5
Experiments
5.1
Benchmark Design
The target benchmark, GranBench-Code, categorizes tasks into four families:
simple, medium, refactor, and recovery (detailed in Table 1). Each task provides
an isolated workspace, source files in a failing or stale state, task metadata, and a
deterministic validator. The recovery family specifically incorporates controlled
failure injection before or after macro execution.
5.2
Execution Harness
We evaluate all variants within a unified execution harness. For each task, the
agent interacts with a disposable after workspace, while a pristine before


snapshot is preserved for auditing. The prompt provides the task description,
workspace context, active tools, and routing decisions. The agent outputs a sin-
gle JSON-formatted action (specifying the skill, arguments, and reasoning) per
step, or a termination signal.
The primitive tool set Sµ includes standard file-system inspection, editing
operations, and test execution. The macro tool set SM comprises high-level com-
posite skills, such as module inspection, verified replacement, and import-aware
refactoring. All variants share the same underlying tool implementations and
differ only in their exposed action spaces. Task success is determined by running
task-specific validators on the final workspace. We track detailed run logs, includ-
ing tool usage, routing decisions, validation results, and total token consumption
across all steps.
5.3
Baselines
We compare several variants using identical LLMs, tools, and verifiers:
– Fixed granularity: A-Micro uses only primitive skills Sµ, and B-Macro
uses only macro skills SM. Neither variant performs recovery.
– Pre-execution routing (No Recovery): C-Heuristic selects the initial
mode using a heuristic rule over pre-execution features. D-Learned-ModeOnly
uses a decision-tree router trained on empirical prior logs.
– Recovery-enabled hybrid execution: E-FSM-Downgrade uses heuristic
routing but explicitly enables a macro-to-micro downgrade transition upon
macro failure. F-Learned-Full employs both the learned mode router and
a learned recovery router.

Dynamic Recovery after Macro Failure
Next, we investigate the need for dynamic recovery upon macro failure by inject-
ing controlled faults into the recovery benchmark (Table 3). For early failures
(Before), lacking a recovery mechanism completely halts progress. Enabling an
explicit FSM downgrade successfully recovers the tasks by falling back to micro
tools, albeit at a higher token cost.
For late failures (After), the macro successfully updates the workspace be-
fore the failure is raised. Consequently, the no-recovery baseline passes valida-
tion without requiring additional actions. In this scenario, the unconditional
FSM downgrade blindly reverts to micro mode, unnecessarily inflating token
costs and execution steps. This tension demonstrates that while unconditional
downgrades guarantee robustness, their overhead necessitates a more selective
recovery policy.

5.8
End-to-End Adaptive Skill Granularity
Finally, we evaluate the full Adaptive Skill Granularity framework by combining
the learned mode router with the learned recovery policy. Table 5 shows that
this combination preserves recovery performance while reducing unnecessary ex-
ecution cost. Under Before faults, F-Learned-Full matches the perfect success
rate of E-FSM-Downgrade with lower token cost. Under After faults, the recov-
ery router skips fallback when the macro has already completed the required
changes, reducing both the transition rate and token consumption compared
with unconditional FSM downgrade.
The same behavior is useful for high-risk structural changes such as module
moves and import rewrites. For module_move_refactor, the refactor-task fea-
ture routes execution through hybrid mode, allowing the agent to recover when
strict no-recovery execution fails. These results show that learned mode selec-
tion and selective recovery complement each other: the former avoids unsuitable
macro execution, while the latter limits fallback to cases where it is actually
needed.
Overall, the proposed framework successfully combines adaptive mode se-
lection with selective recovery, achieving consistently high task success while
significantly reducing execution cost under realistic failure scenarios.
