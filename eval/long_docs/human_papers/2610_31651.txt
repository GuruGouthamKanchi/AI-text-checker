Abstract
Frontier coding agents are becoming increasingly adept at
3D modeling. Yet, they still face challenges when building
objects meant to be assembled in the physical world, often
creating invalid assemblies with floating, colliding, or dis-
connected parts. We argue that providing agents with tools
for assembling builds and verifying their physical feasibility
is sufficient for them to produce physically valid assemblies
that still adhere to input prompts. Focusing on the domain
of LEGO® brick builds, we present BrickWright, a frame-
work for generating physically feasible brick builds from
text or image prompts using pre-trained agents, where a
build is physically feasible if it uses only real parts, has
no colliding or floating parts, and forms a connected struc-
ture if possible. BrickWright guides agents to create builds
by writing code with BrickLayer, a Python toolkit with two
main components: an ergonomic brick assembly API that
halves inference cost compared to working in raw LDraw,
and a validator that provides feedback on physical feasi-
bility. Whereas baseline agents achieve physical validity
rates ranging from only 9% (GPT-6 Luna) to 69% (GPT-6
Astra), BrickWright-guided agents achieve 100% validity on
a sample of 512 prompts, while improving prompt adher-
ence for lightweight agents and maintaining it for stronger
agents. Additionally, they outperform specialized models on
the text-to-brick task. Code is available on our project page:
avalovelace1.github.io/brickwright.

commercially available agents can successfully produce ar-
ticulated objects [45, 59], scenes [52], and constructive solid
geometry models [27]. However, they still face challenges

when building objects for the physical world. We focus on
the task of creating multi-part assemblies: real-world objects
made from a set of prefabricated parts joined by fixed con-
nectors, such as LEGO® builds. Multi-part assemblies must
obey multiple constraints: all parts must be drawn from a
preset library, parts must not collide or float, and the joined
parts typically form a single connected component.
We argue that designing a toolkit for multi-part assembly
creation is sufficient to enable agents to create physically
valid builds. This toolkit should include (1) an assembly API,
which provides an ergonomic programmatic interface for 3D
creation; and (2) a validator, which provides feedback on
a finished build’s physical validity. The need for a toolkit
is independent of how powerful a coding agent is. We ob-
serve that GPT-6 Astra with Codex, when asked to make
brick builds, already writes scripts to generate and validate
its output more than 80% of the time (Sec. D). For complex
physical domains, this self-validation is often not enough,
resulting in builds that do not satisfy physical constraints,
containing colliding, floating, or disconnected parts (Fig. 2).
Even if an agent is powerful enough to write a perfect toolkit,
separately developing a toolkit remains important to reduce
token usage and avoid repeated work. Existing toolkits for
agentic 3D generation [45, 59] are usually intended for digi-
tal asset creation; as they do not consider physical constraints,
they cannot be repurposed as-is to create real-world objects.
We focus on the domain of LEGO® generation as it is
a commonly available yet complex system, consisting of
thousands of parts that connect in dozens of ways. Our
key insight is to merge agentic code-as-3D-models with the
regularity of brick parts. Parts can be modeled as geometries
with localized connectors that have programmatic rules for
assembly (e.g., studs interlock with antistuds). From this
perspective, we leverage the physical production rules for
snap-fit brick builds [6] to create an ergonomic assembly API.
Then, given an image or text prompt, our task is to generate
a program using this API that, when compiled, produces a
LEGO® brick build in the standard LDraw format [21]. This
build should include a list of library part placements, and it
must be physically feasible, having no intersecting or floating
parts and forming a connected structure if possible. While
there are several specialized brick generation methods [10,
11, 19, 36, 37, 48, 50, 53], some of which consider physical
constraints, they generally exhibit worse generalization and
lower fidelity than commercial LLM agents on the same task.
Hence, we wish to achieve this task agentically.
Toward this goal, we introduce BrickLayer, a Python
package for assembling and validating brick builds, along-
side BrickWright, a framework that guides LLM agents
through creating validated brick builds with BrickLayer.
Agents equipped with BrickWright create higher-quality
builds with fewer physical violations; on a test set of 512
prompts, all agents—including lightweight models like
GPT-6 Luna and Claude Haiku 5.5—achieve a 100% va-
lidity score without a significant cost increase or drop in
fidelity. BrickWright is especially useful for lightweight
models: it improves Luna’s performance from 9% to 100%
valid builds and boosts its prompt adherence at 2% the
price of frontier models.

2. Related work
Brick Build Generation. Early work treats brick build
generation as an optimization problem over a target shape.
Legolization [34] voxelizes a 3D mesh, merges voxels into
standard bricks, and iteratively re-merges regions identi-
fied as unstable. Subsequent work captures finer geometric
detail through feature-aware shape approximation and non-
rectangular bricks [57, 58], assembles bricks sequentially via
Bayesian optimization [17], or optimizes Technic assemblies
to match annotated sketches [49]. Retrieval-based methods
map images to figurines assembled from prebuilt templates
[9, 56]. These methods are limited by small brick vocabular-
ies, explicit geometric guidance, or fixed templates.
Learning-based methods generate brick structures directly
from data. These approaches adapt graph generative mod-
els [41], predict voxel representations that are assembled
into bricks algorithmically [4, 24], learn sequential construc-
tion policies [7], or use diffusion to predict labeled voxels
within a single category [10]. Autoregressive methods gen-
erate bricks conditioned on text or images. BrickGPT [37]
fine-tunes an LLM to generate stable structures, but is re-
stricted to eight rectangular brick types across 21 object
categories. LEGO-Maker [11] generates builds from im-
ages, but supports only axis-aligned orientations and two
categories. LegoACE [50] and BrickNet [19] scale to open-
vocabulary generation by training on large collections of
human-designed builds. However, LegoACE learns connec-
tivity implicitly and can produce disconnected components,
while BrickNet represents assemblies as connector graphs
but accumulates collisions over longer build sequences.
Brick-Composer [30] instead approaches assembly from tar-
get views as sequential brick selection and pose estimation,

Agentic 3D Generation. LLM agents have been used suc-
cessfully to create 3D scenes. Recent works use a plan-
execute-critique loop [15, 29] or reconstruct scenes from im-
ages through iterative code execution and visual inspection
[13, 52]. Other works fine-tune LLMs to reason directly over
3D spatial inputs [44] or to generate tool-call trajectories
[14]. These methods place objects in continuous space and
rely on optimization or visual judgment to resolve collisions
and floating objects. In BrickWright, explicit connector rules
enable deterministic checks of attachment validity.
Representing shapes as programs provides structured de-
scriptions of geometry and part relationships [16, 39, 42].
Separately, LLMs have been shown to reason more reliably
when they write code and offload exact computation to an
interpreter [8]. Building on both ideas, agents have been
applied to modeling individual objects as code, typically
through plan-execute-critique loops. Prior work augments
this loop with API retrieval [32], domain-specific languages
[45], or procedural part-based modeling [27], with some
supporting articulation [23, 27, 45, 59]. In CAD, LLMs
have been fine-tuned to generate parametric modeling code
[12, 18, 47], while tool-augmented agents generate and re-
fine parts and assemblies [1, 35, 40, 55]. Articraft [59]
generates articulated assets using a custom SDK and a mini-
mal harness that provides textual feedback from tools that
probe the model code. Unlike these systems, where the agent
generates geometry or infers inter-part relationships, Brick-
Wright assembles fixed parts whose connectors determine
how they attach and move.
Physics-Aware Generation. To improve physical valid-
ity, prior work refines shapes or layouts after generation
[5, 25, 29, 51, 54], fine-tunes generators on simulator feed-
back [26], or guides diffusion sampling with physical con-
straints [33]. Geometric analysis has also been used to plan
LEGO assembly sequences without explicit connector infor-
mation [2]. For brick structures, stability has been assessed
through force-based equilibrium analysis [31, 34, 37] or
physics simulation [17, 46]. In contrast, BrickWright uses
an executable verifier to check for collisions, floating parts,
and connectivity, allowing a pre-trained agent to iteratively
repair builds without task-specific training. Incorporating
force-based stability analysis [31, 34] is a natural extension.
3. BrickWright
Given a natural-language or image description, our task is to
generate a physically feasible brick build from a fixed part
catalog. A brick build is defined as an ordered sequence
of placements. Each placement consists of an element or a
nested brick build, together with a rigid transformation rel-
ative to the containing build. An element specifies a single
part drawn from the catalog and a color. Elements expose
typed connectors, such as studs, whose compatibility and
relative alignment determine valid connections. A build is
3


valid if it uses only catalog parts and contains no colliding
(intersecting) or floating parts. It forms a connected compo-
nent if one can draw a path of connections between any two
elements in the build. We define a build to be physically fea-
sible if it is valid and contains as few connected components
as possible. More complex feasibility considerations, such
as ensuring a build is stable and has an executable assembly
sequence, are left to future work. Note that although having
a single connected component is desirable as it makes a build
less likely to break apart in the physical world, builds with
multiple components are still necessary in some cases: for
example, two separate vehicles in a car chase scene.
We introduce BrickWright (Fig. 3), a framework for gen-
erating physically feasible brick builds using LLM agents.
Using a lightweight harness, BrickWright guides a single
agent to write Python code that produces a brick build us-
ing a custom toolkit called BrickLayer. If the build passes
a set of predefined and agent-written tests, it is accepted;
otherwise, the agent makes edits informed by the test results,
following the commonly used plan-execute-validate loop.
3.1. BrickLayer
LDraw [21], the standard text format for LEGO® builds,
includes no physical validation and is not very ergonomic:
it only allows users to place parts and sub-models by their
absolute 3D poses. This makes it difficult to mate parts
by their connectors or place them relative to others, which
can lead to wasted tokens and misplaced components. To
provide agents with an ergonomic interface for creating and
validating brick builds, we introduce BrickLayer (Listing 1),
a Python package that includes functions for part discovery,
assembly, and validation. BrickLayer provides a unified
programmatic representation for brick builds, enabling them
to be easily understood and edited by humans and agents;
builds can be translated from BrickLayer to LDraw and vice
versa. See Sec. B for BrickLayer documentation.
Discovery. BrickLayer allows users to search the LDraw
catalog [22], which contains 17k+ parts. This search accepts
keywords matched against the part’s official LDraw name.
Results are ordered by their BM25 score [38] multiplied
by a popularity factor that scales logarithmically with the
number of official LEGO® sets containing the part. LDraw
names are parsed into fields such as category, subcategory,
and dimensions; users may target specific fields with their
keyword search and filter results using exact field matches.
Assembly. The central objects of BrickLayer are Element,
representing a single colored part, and LegoBuild, rep-
resenting a brick build.
Both objects support a unified
LegoGeometry interface; this interface exposes dimen-
sions and available connectors, which can be filtered by type
and position. We use BrickNet’s connector annotations [19],
which mark the local frames of the connectors on each part,

For convenience, BrickLayer includes several high-level
construction functions, introduced after noting repeated
patterns in agent-generated code. These include brick,
plate, tile, slope, and inverted slope to in-

multi-component sub-builds; mirror to reflect a build
along a given axis; and fill box, fill slope, and

manner guaranteed to be valid and connected if possible.

BrickNet; snap connections between bricks are so tight that
a naive mesh intersection check would report a false positive.

3.2. Building with BrickLayer
BrickWright is a framework for agentic brick build creation
using BrickLayer. It provides a single agent with a set of
tools and prompts it to create a build by writing and revising
a single Python file in a plan-execute-validate loop, inspired
by Articraft [59]. The BrickWright environment exposes the
tools validate, which runs agent-written tests alongside
fixed collision and floating checks; render, which renders
the build into a multi-view sheet or from a single specified
view; and finalize, which marks the build as finished.
In its system prompt, BrickWright instructs an agent
to make a short internal plan, then write a Python file,
build.py, containing two functions: create build(),
which returns a LegoBuild, and run tests(), which
runs a set of agent-written tests against the completed build.
After creating build.py, the agent is instructed to itera-
tively call validate and edit the build file until all tests
pass, then call render; if it judges the render satisfactory,
it should then call finalize; otherwise, it should revise
build.py and repeat validation. Besides these instruc-
tions, BrickWright includes only the BrickLayer documenta-
tion in its system prompt, and the input text or image in a user
prompt. It does not provide the agent with detailed planning
advice, complete build examples, or building tips beyond the
plan-execute-validate loop; the loop alone is sufficient for
even lightweight agents to produce a feasible build.
BrickWright can be used alongside commercial frame-
works such as Codex, which allows general file access and
script execution. However, to demonstrate its utility alone,
we provide the agent with only two additional tools during
experiments: read / write / insert / edit build to
read and modify build.py, and explore to run a Python
snippet with BrickLayer and the written LegoBuild in
scope, returning its output as text.

Technical details. To test agents with a range of capabilities,
we run experiments with Claude Haiku 5.5 and GPT-6 Luna
(lightweight), GPT-6.1 Sol (balanced), and GPT-6 Astra
(frontier). All agents use High reasoning. Figure examples

the build is connected if it comprises one object. Codex and
Claude Code baselines may read, write, and execute arbitrary
files in a workspace directory, which initially contains only
the LDraw documentation [21] and the library of LDraw
parts [22], including part meshes. BrickWright agents are
only allowed to read and modify the output build.py
and execute text-output-only Python snippets; they have no
access to the LDraw documentation or LDraw part library be-
yond the searchable parts list exposed by BrickLayer. Agen-
tic methods have a budget of $5 per sample; for samples that
reach the budget, we use the latest completed build, whether
valid or invalid. Only Luna w/o assembly API (2 samples)

As Articraft is intended for primitive-based 3D genera-
tion, we minimally modify it to use a library of LDraw part
meshes rather than mesh primitives. Invalid operations on
physical parts (e.g., scaling) are disabled, as are collision
checks, which yield false positives for coupled bricks, and
watertightness checks, which fail on library meshes. We ad-
just Articraft’s system prompt to reword phrases that do not
work with brick builds, such as allowing geometry overlaps.
Metrics. We report metrics on physical feasibility as defined
in Sec. 3; prompt adherence as judged by VQAScore [28],
Perception Encoder [3], and SigLIP 2 [43]; average brick
count per build; and average time and cost per prompt. Va-
lidity and connectivity are first evaluated using BrickLayer’s
validator. Then, to independently verify the metrics’ accu-
racy, we flag potential false positives for review by a human
experienced with LEGO® design. Potential false positives
include collisions resolved by a tested shift of at most 0.2
mm and disconnected components containing parts without
connector annotations. Human review increases collision-
free rates by 0.2 percentage points for BrickNet and Claude
Code (Haiku), 1.4 for Codex (Sol), and 1.0 for Codex (As-
tra). It reduces mean component counts by 0.13 for Codex
(Sol), 0.10 for Codex (Astra), and 0.12 for Articraft; changes
for the remaining methods are below 0.02 components per
build. Numbers in Tab. 1 are post-review.
4.1. Baseline comparison
Compared to vanilla agent baselines, builds produced by
BrickWright-equipped agents exhibit greatly improved phys-
ical feasibility with broadly comparable token costs (Tab. 1).
Impressively, the lightweight model Luna, which has only
