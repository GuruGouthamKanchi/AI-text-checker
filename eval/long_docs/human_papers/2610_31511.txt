DUOCOOK:
AN OVERCOOKED-INSPIRED BENCH-
MARK FOR VISUAL PLANNING AND COORDINATION

ABSTRACT
Coordinating two players in a cooking task requires a vision-language agent to
track changing scene states, sequence recipe steps, and allocate shared resources
under a time budget. We introduce an Overcooked-inspired benchmark for eval-
uating these capabilities in Unreal Engine environments constructed using coding
agents. A single vision-language model controls both players from top-down vi-
sual observations, selecting high-level actions while the engine executes naviga-
tion. The benchmark contains 20 maps in five categories. These categories sup-
port evaluation of centralized coordination under equipment contention, changing
terrain, and handoff dependencies. A prop legend and pot ingredient-count indi-
cators provide explicit visual cues, while grid-based destinations support spatial
grounding. The evaluation compares four VLMs on all 20 maps, measuring task
score, order completion, delivery precision, action acceptance rate, and model
API expenditure. A memory ablation on the same 20 maps examines the effect
of a shared, self-authored notebook while retaining six-response action history in
both conditions. The strongest evaluated model, gpt-6-astra, achieves 26.2%
mean order completion. Notebook memory has mixed score effects across mod-
els, with positive mean differences for Claude and Qwen and negative differences
for GPT and Gemini.

INTRODUCTION
A cooking task can fail even when individual actions appear sensible. A player may chop the correct
ingredient while blocking a board needed for an urgent order, or wait beside a boiling pot instead
of working elsewhere. Efficient cooking requires tracking unfinished operations, assigning comple-
mentary work, and revising schedules as equipment and ingredients become available. This raises a
broader question: can a vision-language model (VLM) use visual observations and structured task
information to coordinate interdependent work under order deadlines?
Overcooked-AI examines cooperation with humans (Carroll et al., 2019), MindAgent studies multi-
agent task allocation (Gong et al., 2024), and Collab-Overcooked introduces resource isolation and
process-oriented evaluation (Sun et al., 2025). Visual-agent benchmarks evaluate interaction across
games, embodied environments, and graphical interfaces (Paglieri et al., 2025; Liu et al., 2025; Yang
et al., 2025). We study centralized scheduling across kitchens with different spatial and operational
constraints, using a common multimodal interface to connect kitchen state, recipes, orders, and
player assignments.
We introduce DuoCook, an Overcooked-inspired benchmark in Unreal Engine where a single VLM
controls two players from a shared context. Its 20 maps span five categories: basic, shared equip-
ment, dynamic, dynamic with shared equipment, and separated workspaces (Section 3.2), introduc-
ing equipment contention, terrain changes, and required handoffs. The model assigns both players’
work to maximize delivery score under deadlines, time-dependent tips, and a streak bonus, making
centralized coordination the evaluation target. Coding agents construct kitchens through SimWorld
Studio (Kang et al., 2026), followed by manual refinement and actor-contract verification (Sec-
tion 3.1).

RELATED WORK
2.1
COOKING ENVIRONMENTS AND COOPERATIVE AGENTS
Overcooked-AI studies coordination and cooperation with humans (Carroll et al., 2019), while
ProAgent uses language models to infer teammate intentions (Zhang et al., 2024a).
MindA-
gent’s CuisineWorld supports centralized multi-agent scheduling (Gong et al., 2024), and Collab-
Overcooked combines resource isolation, asymmetric knowledge, and communication to evaluate
interdependent collaboration (Sun et al., 2025). DuoCook builds on these precedents with one visu-
ally grounded controller for both players and map variations that expose resource and spatial depen-
dencies. It evaluates centralized scheduling rather than inference about an independently controlled
partner; neither multi-cook control nor required handoffs alone constitutes its contribution.
ParaCookZhang et al. (2026) represents cooking tasks as directed acyclic graphs and measures
concurrent execution efficiency.
RobotouilleGonzalez-Pumariega et al. (2025) examines asyn-
chronous, long-horizon planning, while CookbenchCai et al. (2025) combines recipe preparation
with customer-intention recognition. Related planning benchmarks include WORKBENCHQiao
et al. (2025) and Plan-over-GraphZhang et al. (2025b) for graph-structured workflows, Asyn-
cHowLin et al. (2024) for ordering tasks with known durations, and TimeArenaZhang et al. (2024b)
for scheduling in an interactive environment. PACEHuang et al. (2026) overlaps planning and ex-
ecution through interleaved reasoning and action. These directions inform DuoCook’s scheduling
demands, such as preparing another dish while soup boils.
2.2
VISUAL INTERACTION AND GAME BENCHMARKS
Balrog evaluates planning and exploration across games (Paglieri et al., 2025), while VisualAgent-
Bench spans embodied interaction, graphical interfaces, and visual design (Liu et al., 2025). Embod-
iedBench covers semantic tasks, navigation, and manipulation (Yang et al., 2025); VideoGameBench
evaluates raw visual gameplay, including a paused setting that separates some inference-latency ef-
fects from action selection (Zhang et al., 2025a). DuoCook focuses on matched interventions within
cooking workflows. Its engine-executed navigation, grid labels, and structured state assist the con-
troller, so scores are not directly interchangeable with those from different observation and control
interfaces.
2.3
PERSISTENT CONTEXT FOR INTERACTIVE AGENTS
ReAct interleaves reasoning and action using interaction feedback (Yao et al., 2023), while Reflexion
stores verbal reflections across trials (Shinn et al., 2023). DuoCook evaluates a shared notebook of
self-authored observations with age-dependent retention. Removing this notebook while retaining
six-response action history and current visual and structured inputs tests its effect on performance
and inference cost.

GENERATED ENVIRONMENTS FOR EVALUATION
Generated environments can support agent evaluation or serve as the output of a generative model.
Procgen uses procedurally generated levels to evaluate agent generalization (Cobbe et al., 2020),
while MarioGPT generates Mario levels from text (Sudhakaran et al., 2023). In DuoCook, coding
agents build Unreal Engine kitchens from reference layouts and construction instructions, followed
by manual refinement and actor-contract verification (Section 3.1). This process supplies the envi-
ronments for evaluating cooking controllers.

SYSTEM AND TASK DESIGN
Figure 1 summarizes the benchmark workflow, from kitchen construction to controller execution
and evaluation.
3.1
MAP GENERATION WITH CODING AGENTS
We construct kitchens in Unreal Engine using SimWorld Studio, which provides coding agents with
Model Context Protocol (MCP) tools and Markdown skills for scene configuration and asset place-
ment. Two separate claude-opus-5 processes author the generation prompt and build the scene,
respectively. The authoring process reviews the SimWorld Studio architecture, then receives the
game context, a reference image, and an actor naming and scene-structure contract. It produces a
construction prompt with a completion checklist covering required appliances and VLM-controlled
MetaHuman characters. The construction process executes this prompt with access to the game
context, pipeline code, actor contract, and reference image. We then refine the scene manually and
run a script to verify required actors and their names. Manual edits address decoration, collisions,
visibility, and camera configuration. In a truck scene, for example, we moved rocks clear of the
truck bed, adjusted the top-down camera’s yaw, added an isometric camera, and removed a truck
wall to expose the kitchen.
3.2
MAP CONDITIONS
The benchmark contains 20 functional maps based on Overcooked layouts, grouped by equipment
sharing, terrain changes, and item transfers. The main evaluation uses all 20 maps; the memory
ablation uses the same 20 maps. Appendix A lists source levels and evaluation subsets.

All maps contain floors, counters, ingredient bins, pots, plates, chopping boards, and serving points.
Bins, boards, and pots are fixed to counters, which block movement but support food and plate
placement. Players move, carry and place objects, chop ingredients, plate food, and serve dishes.
After serving, dirty plates appear in sinks for washing on sink-equipped maps; otherwise, clean
plates reappear at their initial locations. The map categories vary the coordination required by these
operations. Basic and shared-equipment maps have fixed terrain: the former allow independent
order completion, while the latter require players to share stations such as chopping boards or pots.
Dynamic maps introduce counters or floor sections that move back and forth every 1,000 steps,
changing obstacles or traversable terrain; gaps remain inaccessible, preventing falls. Four dynamic
maps require equipment sharing, and four do not. In separated workspaces, players cannot cross
between regions and must pass ingredients or plates across counters, so neither can complete a dish
alone.
3.3
COOKING TASK AND CONTROLLER OBJECTIVE
A single VLM controls two MetaHuman players to maximize the score from preparing and serving
orders within the episode horizon (Section 4.1). Menus include salads and soups, with recipes and
order queues configured by level. Chopping and dish washing occupy a player throughout execution,
whereas soup boils unattended, allowing concurrent work.
Orders and scoring.
Orders arrive every 1,000 steps, expire after 3,000 steps, and may be fulfilled
in any order. Each delivery earns 20 points plus a time-dependent tip scaled by a combo multiplier:
Ri = 20 + mib(wi),
(1)
where wi is the waiting time at delivery, b(wi) is the base tip (Table 1), and mi follows the schedule
(1, 1, 2, 3, 4), capped at 4. Deliveries build the combo streak; an expired order resets the streak to
zero. The multiplier applies only to tips.
3.4
MULTIMODAL AGENT INPUTS
The controller receives kitchen images alongside task instructions, live state, legal operations, exe-
cution feedback, and six-response action history (Figure 2).
At each decision, both players share a top-down kitchen image with grid labels, a prop legend, and
textual context (Figure 2). A map-specific system prompt of approximately 4,000 words provides
kitchen rules and recipes, using the simulator’s menu, and is re-sent at every decision. Live-state
reports player actions, positions, held items, and station claims, together with orders and preparation
status. Game-UI information is supplied as text to reduce dependence on UI appearance. The
engine lists legal operations based on kitchen state and station claims, without filtering by waiting
orders; rejection feedback explains failures without suggesting corrective plans. Each player’s action
history contains its six most recent responses, newest first, with actions, target cells, and execution
acceptance. This history is retained in both experimental conditions. The memory-enabled condition
additionally supplies a shared, self-authored notebook (Section 4.4).

EXPERIMENTS
Our evaluation examines how a single model coordinates two players under equipment-sharing con-
straints, changing terrain, and required item transfers. It consists of the main benchmark on 20 maps
and a memory ablation on the same 20 maps.

Episode protocol.
Each episode runs for 4,000 steps. This horizon applies to the main benchmark
and the memory ablation. Controller calls follow state-change events, and the simulation pauses
during inference, as described in Section 3.5.
For each map, the initial state, number of orders, and order sequence are fixed and shared across
models and memory conditions. Each model runs once on each of the 20 main-evaluation maps
with memory enabled. For the ablation, we reuse those results on the same 20 maps and run each
model once more on each of those maps with memory disabled. These settings match the starting
conditions and order workload; subsequent trajectories depend on the model’s actions. We compute
metrics for each episode and average them with equal weight across the 20 evaluation maps. Cate-

Commands are counted separately for each player, so a response assigning both players contributes

charges for image inputs and action-history context. We report mean API expenditure per episode
alongside task performance.

4.4
MEMORY ABLATION
We compare controllers with and without shared memory on all 20 maps. The memory-enabled
results are reused from the corresponding main-benchmark episodes. For each model and map, the
memory-disabled run uses the same initial state and order schedule, with only the shared memory
removed.
The shared memory is a notebook the two players fill in themselves. With any decision a player
may attach up to three observations, each a tuple of grid cell, object kind, status, and an optional
free-text note. Both players read the resulting table back on every subsequent call, rendered one
row per observed cell, and each row carries the identity of whoever wrote it. Entries decay on an
exponential forgetting curve with a 600-step half-life and are displayed in three confidence bands
(just seen, fairly sure, hazy); hearsay from the partner decays twice as fast as first-hand observation.
Nothing in it is validated against the simulator: it records beliefs, and a stale or mistaken row is part
of what the condition tests.
The shared store holds entries of the form (grid cell, object kind, status, optional note, author, write
step). Entries are keyed by cell and kind, so a later write about the same cell replaces the earlier one;
this is how a player corrects itself, and a write with status unknown deletes the row instead.

Conditions.
The two conditions differ in one term. Both observations contain the scene image, the
prop legend, the live-state JSON, the operation list, immediate failure feedback, and the six-response
action history; the memory-enabled condition adds the rendered shared store. The action history
appears in both conditions: it is written by the environment rather than the model, is never shared
between players, and is held fixed so that the comparison isolates shared, self-authored memory
from recency alone.
Across the memory-enabled episodes, 40.1% of the entries a player read had been written by its
partner (10,732 of 26,750). This records partner-authored notebook use, but does not by itself show
that the information was unavailable through other inputs.
This design tests whether a shared and decaying world model improves joint performance, and
measures the additional inference cost of maintaining and reading it. Both conditions use the five
benchmark metrics, aggregated over the same 20 maps.

LIMITATIONS
Centralized two-player control leaves communication, private information, and adaptation to inde-
pendent teammates outside the primary evaluation. Top-down observations and engine navigation
reduce demands that would be present under first-person sensing or direct motor control. The prop
legend, pot indicators, live-state JSON, and engine-computed legal-operation list provide additional
information and assistance. Results therefore reflect planning under this combined interface, includ-
ing selection among legal operations to advance waiting orders.
Differences between maps can reflect several task properties, so performance across map conditions
does not isolate the effect of resource sharing. The evaluation also does not isolate the contribution
of the visual legend or pot indicators, which remain fixed. The memory ablation examines the effect
9


of adding a shared notebook while retaining action history, but memory can also change token usage
and latency.
Each model is run once per map and memory condition. Fixed initial states and order sequences
provide matched scenarios, but a single run does not quantify variability in model responses or
establish the stability of model rankings and memory effects across repeated runs.
Generated maps can repeat structural patterns despite visual variation. Shared generation prove-
nance and similar layouts must be considered when defining held-out evaluation. New maps also
do not guarantee that recipes or task concepts are absent from model pretraining. Generalization
beyond the tested kitchen distribution, including transfer to real collaborative work, would require
additional evidence.
Supporting episode logs, per-map metric tables, and analysis scripts are not included in the current
manuscript artifacts. Aggregate results alone do not support a trace-based diagnosis of failures or
independent recomputation of the reported effects.
6
CONCLUSION AND FUTURE WORK
This paper develops the design of an Overcooked-inspired benchmark for visual planning and cen-
tralized coordination in agent-generated Unreal Engine kitchens. Its 20 maps span five categories
covering independent work, shared equipment, changing terrain, and required item transfers. The
evaluation protocol compares four VLMs on all 20 maps using task performance, action acceptance,
and API cost, with a memory ablation on the same 20 maps. Experimental conclusions apply to this
evaluated suite. This provides a concrete way to investigate how a controller turns visual observa-
tions into coordinated cooking actions.
gpt-6-astra achieves the highest mean score (25.6), order completion (26.2%), and action ac-
ceptance (64.6%), while Claude has the highest delivery precision among episodes with deliveries.
Performance remains low, especially on dynamic maps with shared equipment and on separated-
workspace maps. Shared notebook memory increases mean API cost for every model and has mixed
score effects: Claude and Qwen improve in the observed means, whereas GPT and Gemini decline.
These results describe one run per model, map, and condition; repeated runs are needed to assess
the stability of these differences.
